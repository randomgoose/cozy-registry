# Vibe Coding 提交规范与校验

通过 Web 发布页、MCP `publish_component`、Figma Make 等提交的组件代码，是否需要用「标准或指导」来约束？本文档给出建议与可选落地方式。

---

## 一、为什么要约束

| 目标 | 说明 |
|------|------|
| **预览可运行** | 预览页若直接 eval/渲染用户代码，松散代码易导致白屏、报错，影响体验 |
| **安全** | 避免恶意或误用（如 `eval`、动态 `fetch` 任意 URL、访问敏感 API） |
| **AI 可用性** | 结构统一（如默认导出、Props 类型清晰）时，MCP/get_component 更容易被 AI 正确引用 |
| **团队一致** | 命名、格式、依赖范围统一，便于后续搜索、复用和维护 |

不约束的代价：组件质量参差、预览不稳定、难以规模化；过度约束：挫伤 Vibe Coding 的随意性，增加提交门槛。建议**分层**：必须满足的「硬性校验」+ 建议遵循的「指导」。

---

## 二、当前已有校验

- **必填**：`name`、`type`、`title`、`content`
- **名称**：`name` 须为 kebab-case（`/^[a-z0-9]+(?:-[a-z0-9]+)*$/`）
- **类型**：`registry:block` 或 `registry:component`
- **TSX 语法**：`validateTsx(content)` 仅做 Babel 解析，**不做**类型检查、依赖解析或运行时报错检测

尚未做的：代码体积上限、依赖/import 白名单、默认导出与组件命名、禁止危险 API、Props 约定等。

---

## 三、建议的「标准」分层

### 3.1 硬性校验（建议在 API 层强制）

适合在 `/api/registry/items` 与 MCP 发布流程中统一执行，不通过则拒绝提交。

| 项 | 说明 | 实现难度 |
|----|------|----------|
| **TSX 可解析** | 已有 | 保持 |
| **内容长度上限** | 如单文件 ≤ 100KB，防止滥用与存储爆炸 | 低 |
| **禁止明显危险模式** | 如源码中不得包含 `eval(`, `Function(`, `dangerouslySetInnerHTML` 等（可选：仅禁止 `eval`/`Function`） | 中（正则/简单 AST 扫描） |
| **默认导出** | 要求有且仅有一个默认导出，便于预览与 AI 统一 `import Default from "..."` | 中（AST 查 default export） |

### 3.2 软性指导（文档 + 可选 UI 提示）

不强制，但在发布页、文档或 MCP 描述中说明，供人类与 AI 参考。

| 项 | 说明 |
|----|------|
| **组件命名** | 默认导出的组件名建议与 `name` 对应（如 name=`hero-section` → 组件名 `HeroSection`），便于可读 |
| **Props 类型** | 建议用 TypeScript 接口声明 props，便于 AI 生成调用代码 |
| **依赖** | 建议仅使用 React 与项目已支持的库（如 Tailwind），避免无法在预览或消费方运行 |
| **单一职责** | 一个区块/组件做一件事，复杂页面由多个组件组合 |

### 3.3 可选增强（后续按需）

- **Import 白名单**：只允许 `react`、`react-dom`、部分允许的 UI 库，其余拒绝或警告
- **类型检查**：在 CI 或后台对 content 跑 `tsc --noEmit`（需隔离与耗时控制）
- **运行时沙箱**：预览在 iframe + 受限全局环境，即使有危险代码也不影响主站（实现成本高）

## 四、落地方式建议

1. **先文档、后校验**  
   - 在发布页或「帮助」中链到本文档（或精简版「提交须知」）。  
   - 在 MCP `publish_component` 的 description 里写一句：建议符合 Cozy Registry 提交规范（链接或简述）。

2. **硬性校验只加「高收益、低复杂度」项**  
   - 先做：**内容长度上限**（如 100KB）。  
   - 再考虑：**默认导出检测**（AST）；若需要再考虑简单危险模式过滤（正则/AST）。

3. **预览与约束的关系**  
   - 若预览页是直接执行用户代码，建议至少做长度 + 禁止 `eval`/`Function`，再考虑默认导出。  
   - 若预览改为「服务端渲染 + 严格依赖注入」或 iframe 沙箱，再逐步放宽或收紧策略。

4. **与 TODO 的衔接**  
   - 在 [TODO.md](./TODO.md) 中可加一项：「发布校验：内容长度上限 + 可选默认导出/危险模式检查」，待产品与实现优先级确定后勾选推进。

---

## 五、总结

- **是否应该用标准/指导限制？** 建议**要**，但分两层：**硬性校验**保证安全与可预览、可存储；**软性指导**提升一致性与 AI 可用性，不阻塞发布。
- **优先建议**：在现有 TSX 解析 + 必填 + name 格式之上，增加**内容长度上限**；再视需要增加**默认导出检查**与**危险模式过滤**，并把「提交规范」写进文档与 MCP 描述，便于用户与 AI 遵循。
